# Skill Observations Log

세션 중 반복되거나 일반화 가능한 교정/패턴만 기록. 1회성 지엽적 수정은 제외.

## 2026-10-01 — 유니티 작업 세션 (낮/밤 루프, 그래프 분석 포함)

### 1. 존댓말 위반 (반복)
**Issue:** 코드 작업 결과 보고가 아니라, UI 버그 원인을 캐주얼하게 설명/토론하는 톤의 응답에서 반말 어미("~돼", "~해봐", "~틀렸네")가 섞여 나옴. 2회 발생, 매번 사용자가 격하게 항의.
**Improvement:** 진행상황 보고뿐 아니라 기술 설명/디버깅 대화체 응답에서도 문장 끝 어미를 의식적으로 재확인.
**Principle:** 격식 없는 설명 톤을 내리는 것과 반말을 쓰는 것은 별개다 — 톤을 편하게 하면서도 어미는 항상 존댓말을 유지해야 한다.

### 2. 일본어 혼입
**Issue:** 서브에이전트에게 작업을 요약/지시하는 문구를 쓰다가 응답 일부가 한국어 대신 일본어로 나감.
**Improvement:** 여러 언어가 섞인 참고 자료(스킬 문서 등)를 바탕으로 요약문을 쓸 때, 최종 응답 언어가 전부 한국어인지 재확인.
**Principle:** 반말/존댓말 문제와는 별개로 언어 자체가 틀리는 사례가 있을 수 있다 — 응답 직전에 언어 점검 필요.

### 3. 명시적 지시 없이 코드/씬 작업 시작 (반복)
**Issue:** 사용자가 질문/확인("이해했어?", 사실관계 정정)에 답했을 뿐인데, 그걸 작업 승인으로 오해하고 코드·씬을 수정하기 시작함. 2회 발생.
**Improvement:** 사용자의 직전 메시지가 "~해줘/수정해/만들어" 같은 명령형이 아니라면, 질문에 먼저 던진 "~해드릴까요?"가 있었어도 승인으로 해석하지 않는다.
**Principle:** 애매하면 반드시 재확인 질문 후 대기. (이미 memory feedback_no_code_without_explicit_request.md에 기록됨 — 중복 기재.)

### 4. 새 TMP 텍스트에 기본 폰트 미적용
**Issue:** "임시/디버그용 버튼이니까 상관없겠지"라고 가정하고 새로 만든 TextMeshProUGUI에 프로젝트 기본 폰트(성곡세미세리프 SDF)를 적용하지 않음.
**Improvement:** `AddComponent<TextMeshProUGUI>()` 직후 바로 기본 폰트를 설정하는 걸 습관화. 기존 오브젝트 재사용 시에도 폰트를 먼저 확인.
**Principle:** "임시니까 괜찮겠지"라는 예외 처리는 금지 — 프로젝트 전역 규칙은 임시 작업에도 동일하게 적용.

### 5. Unity Editor Play Mode 테스트 시 프레임 미진행
**Issue:** execute_code로 씬 전환/컴포넌트 활성화 직후 바로 런타임 로직(Start() 등)을 검증하려 하면, Game View가 Focus/Repaint되지 않은 상태에서는 `Time.frameCount`가 전혀 올라가지 않아 Start()가 실행되지 않은 채로 잘못된 결과(예: 인스펙터 테스트용 fallback 데이터)를 관찰하게 됨. 여러 번 반복해서야 원인 파악.
**Improvement:** 씬 전환이나 컴포넌트 활성화 직후 런타임 상태를 검증해야 할 때는 `EditorApplication.Step()`을 먼저 호출해 프레임을 강제로 진행시킨 뒤 확인한다. Game View를 GetWindow+Show+Focus하는 것만으로는 부족할 수 있음.
**Principle:** Unity MCP 자동화 테스트에서 "방금 활성화한 오브젝트의 Start()/런타임 상태"를 확인할 때는 항상 프레임 진행을 먼저 보장할 것 — 그렇지 않으면 거짓 양성/거짓 음성 결과를 낸다.

### 6. 비슷한 이름의 UI 영역 혼동
**Issue:** 사용자가 "트레이슬롯area"라고 명확히 지칭했는데 "SlotArea"(퍼즐 보드 슬롯 영역)로 잘못 해석해서 기능을 추가했다가 전부 되돌리는 작업이 발생.
**Improvement:** 유사한 이름(TraySlotArea vs SlotArea 등)이 프로젝트에 공존할 때는 작업 전 하이라키에서 대상 오브젝트 경로를 먼저 확인하고, 애매하면 사용자에게 재확인.
**Principle:** 이름이 비슷한 두 UI 영역이 코드베이스에 존재한다는 걸 알고 있었다면, 추측보다 먼저 하이라키 조회로 검증했어야 한다.

### 7. 커밋 메시지 범위 오류
**Issue:** 실제 `git diff`/`git show --stat`를 확인하지 않고 대화 기억만으로 커밋 메시지를 작성해, 전날 밤 이미 별도 커밋으로 푸시된 내용(가챠 트레이 BlockDrag/GachaManager 변경)을 오늘 커밋 메시지에 중복 기재함. 사용자가 지적해서 `git commit --amend`로 수정.
**Improvement:** 커밋 메시지를 쓰기 전 항상 `git show --stat HEAD`(또는 staged diff)로 실제 포함된 파일을 확인하고, 그 파일들에 해당하는 변경사항만 메시지에 적는다.
**Principle:** 세션 기억은 "무엇을 했는지"는 맞아도 "그게 어느 커밋에 이미 들어갔는지"는 틀릴 수 있다 — 커밋 메시지는 항상 실제 diff 기준으로 작성.
